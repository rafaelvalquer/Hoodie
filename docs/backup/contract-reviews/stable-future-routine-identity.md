# Identidade da previsão de rotina após restauração

O round-trip do APK R8 f69f6e6b, API 37.1 → instalação limpa em API 34, preservou as configurações e todos os registros de 23 dos 24 datasets. Na comparação estrita, `effective_routine_versions` perdeu a linha de ID 4 e ganhou ID 5 com todos os demais campos idênticos. Era a previsão de 20/10/2026, ainda futura no snapshot de origem de 19/10: o histórico vigente/baseline permaneceu igual, mas a identidade exportada sofreu uma substituição desnecessária.

`EffectiveRoutineRepository.prepareTomorrow` fazia `INSERT OR REPLACE` com ID autogerado. O índice único `(epochDay, effectiveFrom)` removia e reinseria até previsões idênticas. A correção compara o registro no mesmo dia/início, não grava conteúdo inalterado e usa `@Update` para uma alteração real, preservando o ID. A comparação/gravação é transacional. Uma versão em outro início de dia, após mudança de fuso, permanece distinta.

Não há alteração em tabelas, colunas, índices, schema Room 12, campos de `BackupSchemaV1`, header HOODIEB1, derivação de chave, serialização ou adapters. `id`, `epochDay`, `effectiveFrom`, `inputKey` e `snapshot` mantêm o contrato V1. Não é necessária migração nem novo formato de backup. A regra de congelamento das versões vigentes/históricas permanece; apenas a previsão futura é revisada quando necessário.

Evidência antes da correção: três testes novos, duas falhas e um controle de fuso aprovado; três atualizações idênticas produziram seis operações SQL e uma atualização real mudou ID 3 para 4. Após a correção, 17 testes direcionados de rotina/persistência/Home passaram sem falhas, erros ou ignorados. Incluem no-op sem gravação, aprendizado real mantendo identidade/histórico de hoje e preservação das versões em diferentes inícios de dia. Resultados brutos locais: `app/build/reports/routine-persistence-qa/`.
